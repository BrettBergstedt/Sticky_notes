# Research Answers

## 1. How HTTP applications preserve state across requests (authentication and session management)

HTTP is a stateless protocol: every request-response cycle is independent, and the server keeps no memory of earlier requests. Web applications therefore add state on top of HTTP by making the client send an identifier with every request. The most common method is the cookie. After a successful login the server creates a session, stores the user's data on the server side, and replies with a Set-Cookie header containing a random session ID. The browser automatically returns that cookie with each later request, and the server uses it to look up the session and recognise the user. Django follows this pattern. SessionMiddleware reads the sessionid cookie and loads the matching row from the django_session table, and AuthenticationMiddleware uses the stored user ID to attach request.user to every request. login() saves the user in the session and logout() deletes it. An alternative is token-based authentication, such as JSON Web Tokens, where the signed token is stored by the client and sent in a header; this suits APIs where there is no browser session. Security matters because the session ID is effectively the user's identity. Cookies should use the HttpOnly, Secure and SameSite flags, sessions should expire, and the ID should be changed at login to prevent session fixation. CSRF tokens, like the csrf_token tag in my forms, stop other sites from submitting requests using a user's cookie.

## 2. Performing Django database migrations to MariaDB

Django talks to MariaDB through its MySQL backend, so the ENGINE value is django.db.backends.mysql. First, install the MariaDB server and create an empty database and a dedicated user, for example CREATE DATABASE sticky_notes CHARACTER SET utf8mb4, followed by CREATE USER and GRANT ALL on that database only. Next, install a database driver in the virtual environment. Django recommends mysqlclient (pip install mysqlclient), which needs the MariaDB or MySQL client libraries and a C compiler on the machine. Then replace the DATABASES setting in settings.py with the ENGINE, NAME, USER, PASSWORD, HOST and PORT (3306 by default), and add OPTIONS with charset set to utf8mb4. Passwords should come from environment variables rather than being written into the code. Because migration files describe changes in a database-independent way, the existing migrations can be reused. Running python manage.py migrate creates all tables in MariaDB, and makemigrations is only needed if the models have changed. To keep existing SQLite data, run python manage.py dumpdata with the natural-key options and excluding contenttypes and auth.Permission before switching databases, then run loaddata after migrating. Finally, confirm the result with SHOW TABLES in the mariadb client or with python manage.py dbshell. MariaDB tables should use the InnoDB engine, because it supports the foreign keys that the models need.
